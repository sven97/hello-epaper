Status Screen Atlas

One skeleton, four zones read top to bottom like a spec sheet — header (title + board + firmware version), status (battery/Wi-Fi/ next-fetch, each with a pixelarticons icon and no word label), action (a real, guaranteed -scannable QR code), and legend (three keycapped buttons) — carrying the status screen, the first-boot onboarding screen, and the connection -failure screen as one visual style instead of three. Every panel is forced to portrait. Title, status, and chrome text are each independently sized off a real firmware font ladder and shrunk to fit the panel's height without losing that hierarchy (title stays the biggest text on the card). Every card mockup renders at true half real size, so they're directly comparable to each other.

How to read this

Title, status, and chrome (the board line, captions, legend) each pick their own size from a ladder of real firmware assets, largest first, stopping at whichever rung the widest line sharing that role actually fits: title 56/42/29/22/16/8px (FreeSansBold 24/18/12/9pt, then classic Font2/Font1), status 42/29/22/16/8px (FreeSans 18/12/9pt, then classic Font2/Font1), chrome 29/16/8px (FreeSans12pt7b, then classic Font2/Font1) — all confirmed compiled in (LOAD_GLCD etc. in the real per-panel setup files). If that width-only pick leaves the card too tall, a second pass shrinks one role at a time down its own ladder until it fits — chrome first, then status, title last, so hierarchy holds instead of whichever role happened to start biggest ending up biggest (an earlier version of this pass let the board line render larger than the title above it on a 400×300 panel; fixed by shrinking in that fixed order, not by size).

Spacing follows the same discipline: one grid unit (the chrome size, the smallest text on the card) and three named multiples of it — a margin, a gap between the four zones, and a smaller gap around the QR alone — instead of a different fraction picked per gap. Battery/ Wi-Fi/next-fetch and the three legend rows share one icon/keycap column width, so their text starts at the same x regardless of what leads each row — and that column's width is now actually subtracted from what those lines' own text-fitting math thinks it has to work with (missing that is what let "strong" render as "stro" on a 104px-wide panel earlier in this pass: the icon was eating real width the fitting pass didn't know about).

Battery, Wi-Fi, and next-fetch each get a pixelarticons icon (MIT licensed, 24×24 grid, rects only — no curves or anti-aliasing to lose, so what's on screen here is what a 1-bit firmware bitmap of the same icon would actually look like) instead of a word label: "battery 98%" is now just "98%" next to a battery glyph that itself swaps between the library's full/medium/low variants by real percent. Shorter lines matter more here than usual — every panel is portrait, and text is what most often runs out of room.

The QR is real, not a placeholder: encoded client-side with the same MIT-licensed qrcode-generator library ported to many languages including the firmware's own ricmoo/QRCode, fixed at type 4 (33×33 modules) and error-correction level L — matching the version/ECC already hardcoded in display.h's drawQrCode() comment. Its module scale is picked the same way computeLayout() picks it — largest scale that fits the remaining budget — checked against width as well as height (a 128px-wide panel exposed a real bug where it wasn't: the QR sized itself off leftover height alone and came out wider than the panel). New this pass: a small QR is worse than no QR — nobody can scan it, and the URL is already shown as text right below it — so 2px/module is enforced as a floor. Below that, the fitting pass keeps shrinking and cutting other content rather than accept a technically -present, practically-unscannable code; that floor held on every one of the 63 states in this atlas, including the smallest panels, without ever having to drop the QR entirely. 2px/module is a starting assumption, not a measured one -- see the open questions.

Content is still the fallback lever for panels where even the smallest real size doesn't fit: each card runs a fitting pass per state, and if something's still too wide at its ladder's floor, or the stack is too tall, or the QR can't clear its scannable floor — checked by measuring the actual text against the real loaded font, and by checking the actual rendered box's height — the single least-essential piece is dropped and the pass repeats: legend detail, then the battery/ Wi-Fi/last-fetch detail suffix, then caption detail, the URL line, the "next" line, the version number, the scan instruction, and the QR itself as an absolute last resort. The note above each table lists exactly what was cut.

Mockups render at true half scale (a 1200×1600 panel shows as 600×800 on screen); the dimension line on each card states the exact on-screen size, the sizes it picked, and whether it was rotated from its native orientation to get to portrait.

Open questions this atlas surfaces

  • 2px/module as the scannable QR floor is a starting assumption, not a measured one. Worth an actual check against a phone camera at each panel's real physical DPI (they range from roughly 130 DPI on the 1.54″ panel to 165 DPI on the 13.3″) rather than one flat pixel number across all of them.
  • Firmware icon integration: don't vendor pixelarticons itself — it's a large SVG set, and this only needs 3 glyphs. Hand-pick battery-full/medium/low, wifi, and refresh, rasterize each to a small fixed size (e.g. 16×16 or 20×20), and convert to 1-bit PROGMEM byte arrays (72 bytes at 24×24 1bpp, so all 3 together cost well under 1KB of flash) in a new src/icons.h, drawn with epaper.drawBitmap() — the same call already available via TFT_eSPI/Adafruit_GFX. One fixed icon size used at every tier (rather than a bitmap per tier) keeps this simple; the icons are small enough that scaling them with the surrounding text isn't likely to matter visually.
  • EE03's color mode. You described it as monochrome; the firmware combo (511) actually drives it as 16-level gray (USE_MUTIGRAY_EPAPER+GRAY_LEVEL16). Worth checking against the panel's real spec — the layout below assumes 16-gray.
  • Onboarding legend wording ("KEY1 Show Screen" / KEY2 & KEY3 blanked) is a first guess — there's no settled behavior for buttons before Wi-Fi is set up.
  • Error state reuses the "scan to open settings" line for the failure reason (e.g. "Wi-Fi failed — scan to check settings") rather than adding a new line, to keep the battery/Wi-Fi/last-fetch lines intact. Alternative: give the reason its own row.
